# F5a / F6c 自主数据与速度—精度优化计划

版本：v1.0｜日期：2026-10-10｜状态：计划与源码审计完成，采集/优化未开始

当前核对：模型会话复用、SHA-256去重、重启恢复已存在，不重复算新增成果。发现重复解码和串行独立步骤是候选瓶颈，尚未用分段计时证实。官方资料web工具未返回可引用内容；MediaWiki文档访问25秒超时、Commons API访问30秒超时。实际运行采集器（`--per-class=1 --max-results=2`）时12次Commons搜索均为 `fetch failed`，manifest保持 `partial`、六类0候选；没有把失败当成数据完成。随后有限探测Open Images官方验证集索引：图片清单约15.3MB、人工标签约23.0MB、框标注约17.1MB、类别描述约11KB均可访问并已暂存系统临时目录；尚未下载图片、尚未映射六类、尚未声称有真值。曾误读不存在的 `tools/face-detector-bridge.js`（退出1），随后核对正确文件为 `tools/local-face-detector.js`；无业务文件修改。

## 1. 任务目标

在不要求用户准备大量照片的前提下，由项目自行收集可追溯的公开样本，建立六类人工可核验评估集；然后以当前版本为基线，寻找能提升文件夹自动识别速度、同时不明显损失分类质量的优化。

本任务不改变网页主入口，不新增复杂设置，不把模型自带标签当作真值，也不把一次本机测速写成普遍性能结论。

## 2. 明确边界

- **数据责任**：默认由项目自动下载、去重、记录来源和生成评估目录；用户不需要提供大量数据。若公开发布视频、截图或数据包，仍需再次检查授权和隐私。
- **隐私**：不扫描用户私人相册，不上传用户照片；公开样本下载只进入 `data/eval/labeled/`，该目录已被 Git 忽略。
- **真值规则**：人工审核后的文件夹标签才是真值。模型预测、CLIP 相似度、文件名和搜索词不能单独作为真值。
- **优化规则**：先测量再修改；每轮只改一个主要变量；候选优化失败就撤销，不为了追求速度牺牲可解释性和 NPU 证据。
- **停止规则**：初始目标为六类每类至少 20 张、总计 120 张唯一图片；最多进行两轮性能优化。达到门槛或两轮均不达标就停止，不无限试模型。

## 3. 数据来源与记录

### 3.1 首选来源

1. **可通过官方 API 获取、带单文件页面和许可元数据的公开图片**：优先 Wikimedia Commons 等可逐文件追溯的来源。
2. **带官方标注和明确许可的公开数据集**：只选能把标注映射到六类、并允许本地评估的子集；下载前记录数据集版本、许可、原始索引文件和校验值。
3. 项目现有公开人像只作回归烟测，不混入六类准确率主统计，除非它具备独立的人工标签和来源记录。

### 3.2 单文件清单字段

`artifacts/public-eval-manifest.json` 必须为每个文件记录：

- 本地相对路径、SHA-256、文件大小、下载时间；
- 来源站点、原始页面 URL、直接媒体 URL、来源 ID；
- 许可名称、署名要求、数据集/版本、是否允许再分发；
- 六类人工标签、标注人/标注方式、审核状态、排除原因；
- 是否与其他文件内容重复、是否为裁剪/变换副本。

缺少许可证或原始页面的文件只能进入临时缓存，不能进入最终评估集；许可证不允许项目分发时，只保留本地评估并在报告中明确“不随项目再分发”。

### 3.3 自动采集器停止条件

计划新增 `tools/collect-public-eval-set.js`，只做有限下载：

1. 按六类查询词和预先允许的来源执行 API 请求，不使用无限翻页或无边界爬虫。
2. 检查 HTTP 状态、内容类型、图片解码、像素上限、文件大小、SHA-256 和重复内容。
3. 对每类收集 30 个候选，人工审核后保留至少 20 个；同一作者、同一事件或连续相似图过多时降采样。
4. 网络超时、来源服务不可用或许可字段缺失时记录失败并切换备用来源，不把下载失败写成数据完成。
5. 收到 120 个合格且已审核的唯一样本后停止；不因为还能下载更多而继续扩大数据集。

## 4. 六类标签审核口径

| 类别 | 最低审核规则 |
|---|---|
| 单人 | 画面中可见且可确认的主要人物为 1 人；不以文件名推断 |
| 多人 | 可确认的主要人物至少 2 人；群像遮挡或极小人物可标待确认 |
| 人物与风景 | 至少 1 人，同时风景/户外环境是明显主体；室内人像背景不算 |
| 风景 | 无主要人物，风景/自然环境是明显主体 |
| 其他 | 可确认不属于以上类别的主体，如动物、建筑、物品、室内静物 |
| 待确认 | 图片损坏、主体过小/遮挡、类别争议或无法可靠判断 |

有争议的图片进入待审池，不强行塞入目标类别。待确认是系统拒识状态，不能把所有未能标注的图片自动当作该类真值；须事先规定可审核的拒识案例。坏图单列失败测试，不混入语义accuracy分母。保留数据集原始人工标注与映射规则；项目由AI代理完成的视觉复核必须标为AI辅助审核，不能冒称独立真人标注。无法获得人类来源标签的结果仅算代理审核集的一致性评估，不能宣称真实准确率已验收。用户只在必要时少量确认。

## 5. 性能基线

在改代码前，基线报告必须同时记录 CPU、核显、独显和 NPU（设备可用时）：

- 初始化时间、单图总耗时、分类推理耗时、文件读取/解码/人脸检测/质量分析分段耗时；
- p50、p95、平均耗时、照片/秒、失败率、峰值 Node RSS；
- 六类混淆矩阵、accuracy、macro-F1、各类别 precision/recall；
- NPU 的 `npuVerified` 和 `VitisAIExecutionProvider` profile 内核证据；
- 样本版本、机器状态、后端、运行次数和是否包含模型初始化。

工程夹具长批继续只证明稳定性；公开人工标签集才用于速度—精度联合判断。基线和候选必须使用同一批、同一顺序规则、同一设备配置，不能拿不同样本的吞吐直接比较。

## 6. 优化顺序

按低风险到高风险执行，每一步都先做局部回归再做联合基准：

### 第 1 轮：减少重复工作

1. 分析源码中的 `sharp` 解码/旋转/缩放路径，尝试共享安全的解码结果或使用 `clone()` 分支，避免同一张图被重复完整解码。
2. 保留现有 SHA-256 跨文件去重和持久状态恢复；只补充经过证明有收益的批内缓存，不能让文件变化后错误复用旧结果。
3. 给每个阶段加测量字段，不改变分类阈值、模型权重和输出类别。

### 第 2 轮：有限并行

1. 评估场景分类、人脸检测和预处理是否能安全重叠；浏览器 FaceDetector、NPU provider 和状态写入若不支持并行，保持串行。
2. 只在 profile 证明等待占主导且资源未过载时尝试并发度 2；不默认开启无限队列，不同时启动多个 NPU session。
3. 对 CPU/DirectML/NPU 分别记录结果；一个设备变快不能推导其他设备也变快。

### 暂不默认做的方案

- 直接改用更小模型、降低人脸输入分辨率、强制量化或跳过人脸检测；这些都可能改变类别边界，必须在第二阶段之后单独评估。
- 将 DirectML 结果称为 NPU；GPU 和 NPU 的 profile 必须继续分开证明。
- 以利用率、温度或单次初始化时间冒充整机能耗或长期性能。

## 7. 联合验收门槛

候选优化只有同时满足以下条件才能保留：

1. **速度**：公开评估集端到端 p50 或 p95 至少改善 10%，且在同设备重复运行中方向一致；若只改善初始化而日常单图无改善，不算通过。
2. **精度**：macro-F1 下降不超过 2 个百分点；任何类别 recall 下降不超过 3 个百分点；不能出现某一类全部塌缩或待确认异常增加。
3. **稳定性**：失败率不增加，重复文件、重启恢复、原图保护、精选幂等回归全部通过。
4. **硬件证据**：NPU 仍必须产生 `npuVerified=true` 和 VitisAI profile 内核；禁止静默回退 CPU。
5. **资源**：Node 峰值 RSS 不超过基线 120%，页面操作和停止服务无回归。

不满足任一门槛就保留基线，记录原因，不继续叠加第二个变量。两轮优化结束后形成“采用/拒绝/未测”的结论并停止。

## 8. 预计文件与证据

120张只作有限试点评估，不足以证明总体精度下降被严格限制在2个百分点。将约80张用于定位/优化、40张按六类分层留作封存验证；同源事件/近重复不得跨分组。报告提供逐样本配对变化与不确定性，小样本无法支持门槛时标“不充分”，不自动通过。不因精度证据不足就无限扩大数据。第1轮与第2轮是最多次数而非必须全部实施；第1轮达标即可停止。

- `tools/collect-public-eval-set.js`：有限下载、去重、许可和 manifest 生成。
- `tools/verify-public-eval-set.js`：逐文件解码、哈希、标签和许可字段检查。
- `tools/benchmark-folder-devices.js`：增加分段计时和标签集入口，保留原有工程基准。
- `tools/local-photo-analyzer.js`：只在 profile 指向明确瓶颈后做最小优化。
- `artifacts/public-eval-manifest.json`、`artifacts/folder-performance-baseline.json`、`artifacts/folder-performance-candidate.json`。
- `docs/performance-baseline-report.md`：记录基线、候选、精度差异、拒绝原因和停止点。

## 9. 执行顺序与停止点

1. 先更新计划和脚本接口，不改默认识别行为。
2. 自动收集并审核 120 张公开唯一样本；若来源不可用，保存失败证据并换备用来源。
3. 生成一次完整基线；没有完整六类标签时只标记 partial，不填写准确率结论。
4. 最多实施两轮优化，每轮单变量、单独报告、通过联合门槛才保留。
5. 到达“速度改善且精度门槛通过”、或两轮均失败、或来源/许可证无法满足时停止。

用户只需在需要公开发布或遇到边界标签时确认；正常采集、整理、统计和工程实现由项目自行完成。
