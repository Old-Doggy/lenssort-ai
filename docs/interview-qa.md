# LensSort AI 面试问答

## Q1：为什么不用云端大模型？

照片具有高隐私属性，且文件夹自动整理需要持续处理大量本地文件。本项目优先本地推理，照片不上传；代价是需要管理模型资源、设备兼容和本地运行时。我把这个取舍写进产品隐私说明，而不是只追求模型能力。

## Q2：你说使用了 NPU，如何证明？

不是通过“检测到 NPU”来证明。照片结果必须有 `npuVerified=true`，并且读取 ORT profile，确认存在 `VitisAIExecutionProvider` 内核。当前 NPU 是 NPU+CPU 辅助算子的混合执行，MediaPipe 人脸检测仍在 CPU/WASM 上运行，所以我不会说是纯 NPU。

## Q3：一键挑好看是审美模型吗？

不是。当前版本是技术质量初筛：清晰度、曝光、主体检测和内容去重。它可以减少明显模糊、曝光风险和重复照片，但不能判断构图、情绪、闭眼或个人审美。我在界面、测试报告和简历中都保持这个边界。

## Q4：如何保证不会误删原图？

原图只读分析，输出使用带哈希的副本；服务不删除、不移动输入文件。精选阶段再次校验源文件路径、符号链接、大小和 SHA-256；源文件变化或路径越界会拒绝复制。验证报告检查了原图字节保持和冲突目标不覆盖。

## Q5：自动分类是如何恢复的？

每个输入文件持久化签名、哈希、分析结果和输出路径。服务重启后读取 `records.json`，相同签名的成功记录不会重新分析；文件发生变化才重新入队。长批测试中 CPU/NPU 各 1,000 个输入重启后重复分析次数都是 0。

## Q6：遇到过什么真实 bug？

千文件测试时发现 Windows 读取状态 JSON 的同时，原子 `rename` 偶发返回 `EPERM`，造成一条记录保存失败。先保留失败报告，再增加临时文件独占创建和有限指数退避；注入错误测试和正式长批都通过。这体现了我会先固定证据再修根因，而不是把失败归因给模型。

## Q7：为什么 NPU 不一定比 CPU 快？

端到端耗时包含模型初始化、provider 缓存、CPU 辅助算子、人脸检测、图片解码、文件复制和状态写入。最新长批 CPU 15.367 张/秒、NPU 13.558 张/秒，包含工程夹具生成等开销；只说明本机管线的观察结果，不是公平纯模型加速比较，也不能推出 NPU 更快或更省电。

## Q8：准确率是多少？

106 张公开候选已完成 AI 辅助视觉复核和四后端代理评估，Accuracy 0.2547、Macro-F1 0.2413、Weighted-F1 0.2899；待确认类没有真值样本，标签不是独立真人真值。因此这不是“真实相册准确率”，且当前代理结果偏低，不能宣称高精度。已停止继续扩展，后续须有独立真值和明确改进计划再重新评估。

## Q9：用户为什么愿意使用？

价值不是“模型很大”，而是减少逐张导入、手动分类和重复筛选。网页只保留两个日常动作，状态和原因可见，用户可以停止，原图不动，精选只是副本。真人接受率仍未测，我不会把自动化脚本当成用户满意度。

## Q10：下一步最重要的产品工作是什么？

当前已到有限工程冻结步，不继续堆模型。剩余外部项是独立六类真值、统一功耗测量条件和 F7.2 真实参与者。拿到条件后只打开对应有限任务，先观察混淆和用户是否理解技术质量边界；模型补充必须先修订计划和验收门槛。

## Q11：需要安装开机启动吗？

不需要。用户双击 `启动网页控制.cmd`，本地服务启动并打开网页，配置一次目录后点击一键筛选即可监听。直接双击静态 `index.html` 不能替代服务；关闭浏览器标签不等于停止后台监听，要点击停止筛选或关闭服务窗口。
